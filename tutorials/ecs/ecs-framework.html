写在最前面：一个必须先纠正的误区

Arc 仓库里没有传统 ECS。

  • Arc 中不存在 arc/ecs/ 目录，没有 Entities.java、Component.java、EntitySystem.java。
  • Arc 只提供了一个轻量事件总线 arc.util.Events（Arc/arc-core/src/arc/Events.java），它不是 ECS。
  • Mindustry 自己实现了一套注解驱动的实体组合系统，业内俗称「Mindustry ECS」，但和 Ash / Artemis / Entt 那种 Entity + Component + System 三元组不是一回事。
一句话：Mindustry 的实体系统本质上是用注解处理器在编译期把多个「能力接口」的方法聚合到一个生成的实体类里。

第 1 章　为什么是「ECS」——从继承树的泥潭说起

1.1 如果 Mindustry 用纯继承会怎样

假设走经典 OOP 继承路线：

Entity
 ├─ PositionedEntity
 │   ├─ RotatableEntity
 │   │   ├─ DamageableEntity
 │   │   │   ├─ Unit
 │   │   │   │   ├─ MechUnit / LeggedUnit / TankUnit / FlyingUnit
 │   │   │   └─ Building
 │   │   │       ├─ StorageBuilding / PowerBuilding / DefenseBuilding
 │   │   └─ Bullet
 │   └─ Decal

三个经典问题：菱形继承爆炸、能力无法复用、新单位类型组合困难。

1.2 ECS 的核心思想：组合优于继承

  • Entity：一个 id 或轻量句柄，本身没有行为
  • Component：纯数据，描述一种能力（位置、血量、武器……）
  • System：遍历拥有某组 Component 的所有 Entity，执行逻辑

1.3 Mindustry 的折中实现

传统 ECSMindustry 等价物
Component（数据）一个 *Comp 类（如 BuildingComp），同时放数据和默认逻辑
Component 接口由编译器从 Comp 类 public 方法签名自动生成的 *c 接口（如 Buildingc）
Entity由 @EntityDef 标注、EntityProcess 生成的具体类（mindustry.gen.Building）
System不存在独立 System 类，每个 Comp 自己有 update()
Entity-Component 绑定编译期固定，运行时不能增删
一句话总结：Mindustry 的「ECS」= *Comp 类定义能力 + @EntityDef 注解声明组合 + EntityProcess 编译期生成聚合实体类。

2.4 实体生命周期

create()  →  add()  →  每帧 update()  →  remove()  →  （可选）回收进池
  1. 创建：Building.create() 静态工厂 new 出实体
  2. 加入世界：add() 塞进 Groups.build / Groups.unit

  4. 移除：remove() 从 group 摘掉；pooled=true 时回池

// :1241
protected void initBuilding(){
    try{
        Class<?> current = getClass();
        if(current.isAnonymousClass()) current = current.getSuperclass();
        subclass = current;

        while(buildType == null && Block.class.isAssignableFrom(current)){
            Class<?> type = Structs.find(current.getDeclaredClasses(),
                t -> Building.class.isAssignableFrom(t) && !t.isInterface());
            if(type != null){
                Constructor<? extends Building> cons = (Constructor<? extends Building>)type
                    .getDeclaredConstructor(type.getDeclaringClass());
                buildType = () -> {
                    try{ return cons.newInstance(this); }
                    catch(Exception e){ throw new RuntimeException(e); }
                };
            }
            current = current.getSuperclass();
        }
    }catch(Throwable ignored){ }

    if(buildType == null){
        buildType = Building::create;   // :1276 兜底
    }
}
mod 作者必须理解：每个 Block 子类通常写一个非静态内部类 class XxxBuild extends Building。initBuilding() 反射拿到这个内部类构造器。如果你只 extends Building 而不写内部类，buildType 会走 Building::create 兜底，你覆写的所有钩子都不会生效。

第 6 章　模组能碰什么——钩子清单 重点

6.1 模组不能做的事

注解处理器在游戏编译期运行，mod 在游戏启动后加载：

  • ❌ 不能新增 *Comp 类（不会被 EntityProcess 聚合）
  • ❌ 不能运行时给实体增删 comp
  • ❌ 不能修改 gen 生成的类
  • ❌ 不能改变实体由哪些 comp 组成

6.2 模组能做的事

  1. ✅ extends gen 接口 / 官方 Building 子类：class MyBuild extends Building 或 extends WallBuild
  2. ✅ 覆写 comp 中定义的钩子方法（isFinal = false 允许覆写）
  3. ✅ 用 Events 系统做跨实体协作
  4. ✅ 用 Vars.content / Blocks / Units 注册新内容

6.5 完整可复制的代码示例

下面实现一个「热力导管」：把热量沿 proximity 邻居做双缓冲传递。这正是官方 HeatConductor 和很多热力学 mod 的核心思路——不需要新增 comp，只覆写 update() 和 onProximityUpdate()。

package yourmod.content;

import arc.scene.ui.layout.Table;
import mindustry.Vars;
import mindustry.world.Block;
import mindustry.world.Tile;
import mindustry.gen.Building;

/**
 * 自定义热力导管：沿邻居做双缓冲热量传递。
 * 适用版本 v159.7
 */
public class HeatConductor extends Block{

    public float heatConductivity = 0.25f;
    public float maxHeat = 100f;

    public HeatConductor(String name){
        super(name);
        solid = true;
        update = true;          // 告诉游戏这个建筑需要每 tick 更新
        configurable = false;
        destructible = true;
    }

    public class HeatConductorBuild extends Building{
        public float heat;       // 当前热量
        public float nextHeat;   // 双缓冲：下一 tick 的热量

        @Override
        public void placed(){
            super.placed();
            heat = 0f;
            nextHeat = 0f;
            for(Building b : proximity){
                if(b != null) b.onProximityUpdate();
            }
        }

        @Override
        public void onProximityUpdate(){
            super.onProximityUpdate();
            // 邻居集合由 BuildingComp 自动维护在 proximity 字段（:69）
        }

        @Override
        public void updateTile(){
            heat = nextHeat;

            float neighborSum = 0f;
            int validNeighbors = 0;
            for(Building b : proximity){
                if(b instanceof HeatConductorBuild other){
                    neighborSum += other.heat;
                    validNeighbors++;
                }
            }

            float avg = validNeighbors == 0 ? 0f : neighborSum / validNeighbors;
            nextHeat = Math.max(0f, Math.min(maxHeat,
                heat + (avg - heat) * heatConductivity));
        }

        public void acceptHeat(float amount){
            nextHeat += amount;
        }

        @Override
        public void displayBars(Table table){
            super.displayBars(table);
            addBar(table, () -> "heat",
                () -> (heat / maxHeat),
                () -> Vars.media.heat);
        }

        @Override
        public void write(arc.util.io.Writes write){
            super.write(write);
            write.f(heat);
            write.f(nextHeat);
        }

        @Override
        public void read(arc.util.io.Reads read, byte revision){
            super.read(read, revision);
            heat = read.f();
            nextHeat = read.f();
        }
    }
}

要点：

  • update = true：Block 字段，没有它 updateTile() 永远不被调
  • 双缓冲：避免同 tick 内 A→B→C 传两次导致能量不守恒
  • proximity：BuildingComp.java:69 自动维护
  • write()/read()：自定义字段必须序列化

6.6 ECS 设计对 mod 写作的启示

  • 不要尝试造新 comp。想加「热量」？直接在 XxxBuild extends Building 子类里加 public float heat 字段就行。Building 本身已经是万能容器。
  • 跨实体交互走 proximity + Events。
  • 钩子是你的全部武器。官方假设你只能 extends 一个 Building 子类 + 覆写钩子。学会这几个钩子，95% 的 mod 需求都能 cover。

7.4 代码示例：mod 级全局逻辑

package yourmod;

import arc.Events;
import mindustry.game.EventType.*;
import mindustry.game.Trigger;
import mindustry.mod.*;

public class HeatMod extends Mod{

    public static HeatNetwork net;

    public HeatMod(){
        // 1) 进图时初始化
        Events.on(WorldLoadEvent.class, e -> {
            net = new HeatNetwork();
            net.rebuildAll();
        });

        // 2) 建筑放置时，重连热力网络
        Events.on(BlockBuildEndEvent.class, e -> {
            if(!e.breaking && e.build != null){
                net.onBuildPlaced(e.build);
            }
        });

        // 3) 每 tick 驱动全局热流
        Events.run(Trigger.update, () -> {
            if(net != null && !Vars.state.isPaused()){
                net.tick();
            }
        });
    }
}
注意：Events.run(Trigger.update, ...) 注册的回调在 mod 整个生命周期内存在，世界重开时记得在 WorldLoadEvent 里重置你自己的数据，否则会跨图泄漏。

A.5 架构一句话版

Mindustry 没有传统 ECS；它用 @EntityDef 标注 comp 组合，由 EntityProcess 在编译期把多个 *Comp 类的字段和方法聚合进 mindustry.gen.Building / mindustry.gen.Unit 等具体类；mod 作者只能 extends 这些生成类并覆写钩子，跨实体协作靠 Arc Events 总线。
