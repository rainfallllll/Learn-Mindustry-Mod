1. 概述

1.1 方案总览

《热力学系统设计手册》提出了一套以热量 Q 为唯一状态变量、温度 T=Q/C 为表观结果的模块化热交换系统。核心设计包括：

  • 双缓冲结算：Phase 1 只写 pendingDeltaQ，Phase 2 统一结算，消除遍历顺序依赖
  • 惰性温度：tempDirty 缓存避免每 tick 重复除法
  • 建筑间独立热阻 R：R_AB = R_A + R_B（串联），与环境传热系数 airU 完全独立
  • 双轨环境温度表：T_ground（每 tile）+ T_air（全局），进图预计算
  • 地块效率系数：groundEfficiency 查表 + maxHeatRate 上限
  • 五类建筑：产热锅炉 / 恒温耗热精炼炉 / 温差发电机 / 档位热泵 / 一体化管道

1.2 评估方法

对设计方案中列出的 10 个核心机制，逐条在 Mindustry v159.7 源码中查找对应的基础设施，输出判定、源码依据、模组实现建议和风险注意事项。

1.3 总体判定

方案整体可行。 所有核心机制均有 Mindustry 原生基础设施支撑，无需修改游戏源码。主要适配点集中在：环境温度需自建存储（Floor 类无温度字段）、每 tick 驱动需通过 Events 系统注册、建筑列表需手动维护增删。

2. 逐条机制评估

2.1 核心双缓冲循环 原生支持
Phase 1 只读温度写 pendingDeltaQ / Phase 2 结算，消除遍历顺序依赖。
源码依据
  • BuildingComp.update() 每 tick 调用：BuildingComp.java:2270
  • Trigger.update 枚举值：EventType.java:47
  • Events.run(Trigger, Runnable)：Arc/Events.java:19
实现建议

在 ThermalModMain.init() 中调用 Events.run(EventType.Trigger.update, () -> thermalSystem.update(1f)) 驱动每 tick 更新。ThermalSystem 内部维护 Seq<ThermalBuilding> 列表。

风险

Trigger.update 在客户端和服务端都会触发，多人模式下需确认热力计算只在服务端运行。遍历 Seq 时不能修改集合，增删需在 placed()/onRemoved() 中维护。

2.2 防过冲 flow=min(flow, storedHeat) 原生支持
限制传热量不超过自身存量，杜绝温度穿越与负值。
源码依据 纯 Math.min() 运算，无需游戏 API。
实现建议 Phase 1 中 flow = Math.min(flow, myNode.storedHeat)。addHeat() 中已有 if (storedHeat < 0f) storedHeat = 0f 防负兜底。
2.3 惰性温度 T=Q/C（tempDirty 缓存） 原生支持
温度不实时计算，只在 getTemperatureK() 被调用时惰性求值，用 dirty 标志缓存。
源码依据 纯 Java 逻辑。
实现建议 ThermalComponent 维护 cachedTempK + tempDirty。addHeat() 标记 dirty，getTemperatureK() 检查 dirty 后求值。
风险 Phase 1 中调用 getTemperatureK() 清除 dirty；Phase 2 中 addHeat 又标记 dirty——这是正确的，因为 Phase 2 的环境换热需要重新求值。
2.4 建筑间独立热阻 R（串联 R_AB=R_A+R_B） 原生支持
建筑间传热使用独立热阻 R，与 airU 无关。两端串联相加。
源码依据
  • BuildingComp.proximity 邻居数组：BuildingComp.java:69
  • onProximityUpdate()：BuildingComp.java:1159
  • 原版热传导参考：HeatConductor.java:54
实现建议 Phase 1 遍历 building.proximity，检查邻居是否 instanceof ThermalBuilding。flow = dT / (myR + neighborR) * dt。只向低温传热避免重复。
风险 proximity 是 transient，反序列化后自动重填。大块建筑多邻居，每个邻居独立计算热流。对角线建筑不在 proximity 中。
2.5 环境查表（双轨温度表，进图预计算） 需适配
进图时遍历所有 tile 预计算地温，全局气温单独存储。运行时 O(1) 查表。
源码依据
  • Floor 类无温度字段：Floor.java:28 起仅有 speedMultiplier/dragMultiplier 等
  • WorldLoadEvent：EventType.java:107
  • Tile.pos()：Tile.java:73（Point2.pack 打包坐标）
  • Tile.array()：Tile.java:78（线性索引 x + y*width）
  • Tile.floor()：Tile.java:187
  • Tiles.eachTile(Cons<Tile>)：Tiles.java:122
  • Vars.world.tiles：World.java:33
实现建议 用 FloatArray groundTemps（大小 width*height），按 tile.array() 索引。材质温度表用 ObjectMap<String, Float>。监听 WorldLoadEvent 预计算。
风险 注意设计文档说"按 tile.pos() 索引"，但 pos() 是 Point2.pack 打包坐标，与 array() 的 x+y*width 不同。实际应使用 array()。WorldLoadEvent 时建筑尚未加载，但 tile 已就绪。
2.6 地块效率系数 groundEfficiency + maxHeatRate 需适配
建筑声明面对不同地块的效率系数，地块声明最大热交换速率。实际换热 = min(airU × groundEff × ΔT, maxHeatRate)。
源码依据 Block.attributes：Block.java:186；Attribute.add(String)：Attribute.java:62。但 Attribute 系统不适合直接存 maxHeatRate。
实现建议 groundEfficiency 用 ObjectFloatMap<String> 存在 ThermalComponent 中。maxHeatRate 在 EnvironmentTemperature 中维护查表。不需要扩展 Attribute 系统。
风险 Floor 名称匹配需确认。"air" 是虚拟条目，用默认 1.0 处理。
2.7 isFloating 架空只与空气换热 原生支持
isFloating=true 的建筑只与空气换热；false 的同时与空气和地面换热。
实现建议 布尔字段，Phase 2 中始终算空气换热，仅 !isFloating 时算地面换热。
风险 不要与 Block.floating 原版标志混淆——那是"可悬空放置"，这是我们自己的"不与地面换热"。
2.8 五类建筑 原生支持
锅炉/精炼炉/温差发电机/热泵/管道，各自实现 updateThermalLogic。
源码依据
  • Block(String name)：Block.java:444
  • Build 类模式参考：HeatConductor.java:54（extends Building）
  • updateTile() 覆写：BuildingComp.java:2017
  • placed()：BuildingComp.java:1361；onRemoved()：BuildingComp.java:1398
实现建议 每个建筑继承 Block，内部 Build 类继承 Building 并实现 ThermalBuilding 接口。Block 构造函数自动注册（Content.java:20-23）。
风险 热泵双端需要两个 ThermalComponent，与现有单节点接口不兼容，本轮只给骨架。
2.9 面板显示 display(Table) 原生支持
在建筑信息面板中显示温度、热量、热容、运行状态等。
源码依据 display(Table table)：BuildingComp.java:1561；displayBars(Table)：BuildingComp.java:1667。
实现建议 Build 类覆写 display(Table)，先调 super.display(table)，再添加热力信息行。用 table.label(() -> ...) lambda 自动刷新。温度转摄氏：getTemperatureK() - 273.15。
2.10 性能（每 tick 遍历所有热力建筑 × 邻居） 原生支持
每 tick 遍历所有热力建筑及邻居计算热流。
实现建议 Phase 1：N × K/2 次热流计算；Phase 2：N 次环境换热 + 自身逻辑。总计约 20N FLOPs/tick。
风险 500 个热力建筑约 10K FLOPs/tick，无压力。超 1000 需考虑分区域更新。

4. 性能评估

4.1 每 tick 计算量估算

Javapseudocode
设 N = 热力建筑数量，K = 平均邻居数（约 4）

Phase 1（接触热流）：
  - N 次 getTemperatureK()（惰性，约 N 次除法）
  - N × K/2 次热流计算（只向低温传热）
  - 每次热流：1 除法 + 2 乘法 + 2 加法 ≈ 5 FLOPs

Phase 2（结算 + 环境换热 + 自身逻辑）：
  - N 次 addHeat(pendingDeltaQ) + 清零
  - N 次空气换热：2 乘法 + 1 减法 ≈ 3 FLOPs
  - N × 0.8 次地面换热（20% 架空）≈ 4 FLOPs
  - N 次 updateThermalLogic(dt) ≈ 2~10 FLOPs

总计每 tick：约 20N FLOPs + 2NK 次比较

4.2 建筑数量上限建议

场景N每 tick FLOPs评估
小型基地50~1,000完全无压力
中型工厂200~4,000流畅运行
大型热网500~10,000可接受
超大规模1000+~20,000需优化

建议：当前实现可支撑 500 个热力建筑 流畅运行。

5. 存档与网络

5.1 序列化需求

数据序列化说明
storedHeat需要核心状态，读档后恢复
pendingDeltaQ不需要每 tick 清零，临时缓冲
heatCapacity / airU 等不需要来自 Block 定义
groundTemps不需要进图预计算，重进图重建
airTemperature不需要全局常量

5.2 多人同步

  • storedHeat 随 Building 序列化字段自动同步
  • 客户端通过 getTemperatureK() 本地计算显示温度
  • pendingDeltaQ 不需要同步（每 tick 清零）
  • placed() 中有 if(net.client()) return; 判断——建筑列表增删应在服务端
  • Events.run(Trigger.update, ...) 两端都触发，需用 !net.client() 守卫

6. 总体结论

方案完全可行。 所有核心机制在 Mindustry v159.7 中均有对应基础设施，无需修改游戏源码。
